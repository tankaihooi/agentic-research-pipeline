## Chapter 3: Weaviate (The Hybrid Search Revelation)

I moved to Weaviate for one specific reason: a user typed “INV-2024–8832” into the search box.

Pure semantic search completely failed. The embedding for “INV-2024–8832” had no strong semantic representation — it’s a unique invoice identifier, not natural language. The model returned invoices that were semantically related to “invoice numbers” in general, not that specific invoice.

This is a known failure mode of dense vector search.

Pure dense vector search has a well-documented failure mode: it handles semantic similarity well but fails on exact keyword matches, product codes, proper nouns, and any token that does not have a strong learned representation. A query for “invoice INV-2024–8832” in a dense-only system will retrieve semantically similar invoices rather than that specific invoice.

The solution is **hybrid search**: combine semantic search (vectors) with keyword search (BM25). Weaviate has this built in.

The invoice was now the first result. The `alpha=0.5` blend gave enough weight to keyword matching that exact identifiers scored high, while semantic matching still caught natural language queries.

Weaviate has built-in hybrid search (semantic + keyword), built-in vectorization, and multi-modal support out of the box.

This was the capability I needed and didn’t have with pgvector or Pinecone.

pgvector *can* do hybrid search, but it requires installing pg\_trgm or using a full-text search column separately, then writing the fusion logic yourself. Weaviate has it as a first-class feature with a clean API.

### The Pain Points

**Schema changes are painful.** Weaviate requires defining your schema upfront. Changing it later (adding a property, changing a data type) requires careful migration steps. With pgvector, adding a column is `ALTER TABLE`. With Weaviate, it's more involved.

`ALTER TABLE`

**Operational complexity.** Weaviate is a separate service you’re now running. Unlike pgvector (which is just Postgres, which you’re already running), Weaviate needs its own Docker container, its own backup process, its own monitoring.

**The learning curve is real.** The documentation is good, but the object model, collections, cross-references, and consistency model all need to be understood. More concepts than “it’s just Postgres.”

This isn’t a satisfying “one winner” conclusion. But it’s the honest one.

If I was starting fresh with knowledge of what I know now:

**Under 5M vectors, already running Postgres:** pgvector, immediately, no second thought. The cost is zero, the integration is seamless, and the performance is more than sufficient for 99% of use cases.

**Need zero ops overhead, don’t care about cost:** Pinecone. It’s the fastest path and the ops burden is genuinely zero.

**Need hybrid search as a first-class feature:** Weaviate (self-hosted to control costs).

**Over 10M vectors, performance-critical:** Look at Qdrant or Milvus — purpose-built, Rust-based, better performance characteristics at extreme scale than any of the three above.
