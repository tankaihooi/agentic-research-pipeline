## 1. pgvector: the default that wins more often than people expect

**Why it works in production:** You already have Postgres. Your team already knows Postgres. Your backup, replication, monitoring, and security tooling already work with Postgres. Adding vector search becomes a one-line install instead of a new system to operate.

## 2. Pinecone: the managed default for teams that want to stop thinking about infrastructure

**What it is:** A fully managed, purpose-built vector database. Closed source, cloud-only, available on AWS, GCP, and Azure regions.

**Why it works in production:** Pinecone removes every operational concern. No index tuning, no replica management, no backup configuration. You write to an API and Pinecone returns relevant vectors. For teams without dedicated database engineers, this matters.

**Where it shines:** Pure vector workloads where retrieval latency under 50ms at p99 is non-negotiable, multi-tenant SaaS apps where each tenant gets isolated namespaces, teams that prioritize developer velocity over infrastructure control.

**Where it breaks:** Cost. At scale, Pinecone gets expensive fast. We’ve seen $40K/month bills for workloads that would cost $4K/month on self-hosted alternatives. No self-hosting option means it’s a non-starter for regulated industries needing data residency.

## 4. Qdrant: the performance pick when filtering matters

**What it is:** Open-source vector database written in Rust. Self-hosted or managed cloud (Qdrant Cloud). Built for high-throughput filtered vector search.

**Why it works in production:** Qdrant’s payload filtering is genuinely fast. Where Pinecone and Weaviate slow down on metadata filters, Qdrant maintains performance because filtering is part of the indexing pipeline rather than a post-retrieval step. Recent releases widened that edge: Qdrant 1.17 added binary quantization (up to 40x memory reduction) and relevance-feedback queries for iterative search refinement.

The filter is not a second pass over the results. It is applied while the index is traversed, which is why latency stays flat as filters get more specific.

**Where it shines:** Workloads with heavy metadata filtering (e-commerce search with category + price + availability filters, recommendation engines with user-segment filtering), high-throughput scenarios where p99 latency matters.

**Where it breaks:** Smaller community than Weaviate or Milvus. Managed cloud is newer and less mature than Pinecone’s offering.

**Real production note:** We pick Qdrant when the workload involves filter-heavy retrieval at high QPS. For one e-commerce client, switching from Pinecone to Qdrant cut their p99 retrieval latency from 180ms to 32ms on the same hardware footprint.

**Pricing:** Free self-hosted. Qdrant Cloud starts at $0.01/hour for dev clusters, scales with cluster size.

## 5. Milvus / Zilliz Cloud: the choice for billion-scale vectors

**What it is:** Open-source vector database designed for massive scale. Milvus is the open-source project; Zilliz Cloud is the managed offering from the original team.

**Why it works in production:** Milvus is built for the case where you have over 100 million vectors and need sub-second retrieval. Distributed architecture with separate query, index, and data nodes that scale independently.

**Where it shines:** Image search at scale (think Pinterest-style billions of embeddings), video understanding pipelines, large-scale recommendation systems, scientific research datasets.

**Where it breaks:** Operational complexity is real. Milvus is a distributed system with multiple components, each with its own scaling and tuning concerns. Overkill for anything under 10M vectors.

**Real production note:** Milvus is the right answer twice a year for us, on average. The other 50 deployments don’t need it. When you need it, nothing else comes close. When you don’t need it, it’ll cost you weeks in operational overhead.

**Pricing:** Free self-hosted. Zilliz Cloud Serverless starts at $0/month with usage-based pricing.

## 5 patterns I see across enterprise vector database deployments

After 100+ deployments, certain patterns repeat often enough to be predictable. These are the ones that matter most.

## Pattern 1: Most teams over-engineer the vector DB choice in week one

The most common mistake is picking a “purpose-built vector database” before knowing what your workload actually looks like. Pinecone for a 100K-vector RAG system is overkill. Milvus for a prototype is operational suicide. Start with pgvector or Chroma, hit a real bottleneck, then migrate. The migration is rarely as expensive as people fear.

## Pattern 2: Filter performance breaks more deployments than vector recall

Recall improvements above ~95% are typically not the bottleneck. Filter performance is. When your application needs `WHERE tenant_id = X AND timestamp > Y AND vector similar to Z`, the difference between "fast" and "slow" vector DBs becomes obvious. Test filter+vector queries before committing.

## Pattern 3: Cost predictability matters more than absolute cost

A managed vector DB at $4K/month with predictable scaling beats a self-hosted DB at $1.5K/month that randomly spikes to $12K. CFOs sign capped infrastructure budgets. They struggle with usage-based bills without a ceiling.

## Pattern 4: Sovereignty constraints get discovered late in the project

Enterprise compliance teams ask “where does our data go?” in week 10, not week 1. By then, the wrong choice means a 6-week rebuild. For any deployment with regulated data (healthcare, fintech, legal, defense), pick a vector DB that supports self-hosted deployment from day one — even if you’re starting in a managed environment.

## Pattern 5: Hybrid search becomes a requirement faster than expected

Pure vector search rarely stays pure. Within 90 days of production deployment, every RAG system we’ve built has added some form of hybrid retrieval (vector + keyword + metadata filtering). Picking a vector DB with native hybrid support saves a major refactor.

## Is pgvector good enough for production?

Yes — pgvector is production-ready for RAG systems with up to 50–100 million vectors. Beyond that, HNSW index rebuild times become a constraint, and dedicated vector databases like Qdrant or Milvus become a better choice. We’ve shipped pgvector to production for over 30 enterprise clients without scale-related issues.

## What is the difference between pgvector and Pinecone?

pgvector is a Postgres extension that adds vector search to an existing Postgres database. Pinecone is a fully managed, purpose-built vector database with no self-hosted option. Pinecone offers better performance at a very large scale and reduces operational overhead, but it costs significantly more and compromises data sovereignty for regulated industries. For self-hostable private LLM deployments, pgvector is often the only viable choice.

## Which vector database is fastest?

For raw retrieval speed at a moderate scale, Qdrant typically benchmarks fastest among open-source options due to its Rust implementation and indexing strategy. At the billion-vector scale, Milvus is purpose-built for distributed performance. For sub-millisecond latency on small datasets, Redis with vector search is hard to beat. The honest answer is that “fastest” depends on your workload shape — filter-heavy, scale, latency tolerance, and concurrency all matter.

## Can I use Postgres as a vector database?

Yes — Postgres with the pgvector extension is a fully functional vector database that handles similarity search, hybrid retrieval, and filtering. For most teams already operating Postgres, adding pgvector is a one-line installation and lets you avoid maintaining a separate database system. This is the default we recommend for new RAG projects unless there’s a specific reason to choose otherwise.

## Is Pinecone worth the cost?

Pinecone is worth the cost when developer velocity outpaces infrastructure cost — typical for early-stage startups with small engineering teams. It becomes hard to justify at an enterprise scale where the same workload on self-hosted Qdrant or Milvus costs 5–10x less. For regulated industries needing data sovereignty, Pinecone is a non-starter regardless of cost.

## What is the best open-source vector database?

Open-source vector databases worth evaluating in 2026: pgvector for general use, Qdrant for performance and filtering, Weaviate for hybrid search, Milvus for billion-scale, Chroma for prototyping, and LanceDB for multi-modal. There is no single “best” — the right choice depends on workload shape, existing infrastructure, and team expertise.
